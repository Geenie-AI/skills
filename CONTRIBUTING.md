# Contributing

Thanks for improving a skill or adding one. Start with
[`docs/skill-pattern.md`](docs/skill-pattern.md); it is the contract every
skill in this repository follows, and the validator enforces most of it.

## Before you open a pull request

```bash
python3 scripts/validate.py              # static checks, no model needed
for f in scripts/*.sh; do bash -n "$f"; done
```

The validator fails on host tool names in a skill (H1), unresolved relative
links (H4), host-specific frontmatter keys (H3), line budgets, duplicate or
missing rule IDs, broken scenario fixtures, missing harness files, a
marketplace entry whose version differs from the repository version, and
adapter READMEs that do not point at the shared skills folder. It warns when
the README catalogue is out of date; `python3 scripts/skillrepo.py sync`
regenerates it (the `catalog` workflow does the same on `main`).

## What a change needs

| Change | Also needs |
|---|---|
| A model-facing file under `skills/<name>/` | An entry under `## [Unreleased]` in `CHANGELOG.md`, in the skill's group (checked on pull requests) |
| A rule, scope, target or host overlay | A scenario in `tests/<name>/scenarios/` with `expected-checks.md` citing the rule |
| A host fact (path, flag, frontmatter key) | Verified against the host's current docs, or marked `verify:` with the URL, in `adapters/` |
| A new rule ID | Defined exactly once, as a bold bullet or a table row whose first cell is the ID |
| A new skill | Scaffolded with `scripts/new-skill.sh`, with planning documents and at least one scenario; the catalogue row and marketplace entry are generated from its description |
| A skill's `description` | Nothing by hand: the catalogue and marketplace entry are regenerated by `scripts/skillrepo.py sync` and the `catalog` workflow |
| Shared tooling (`scripts/`, `adapters/`, workflows) | An entry under "Repository" in `CHANGELOG.md`; every skill still validates |

## Adding a skill

```bash
scripts/new-skill.sh <name>
```

creates `skills/<name>/`, `tests/<name>/` and `planning/<name>/` from
`template/` and generates the catalogue row and marketplace entry. Then:

1. Write `planning/<name>/` first: what the skill does and declines, the rules with IDs and the source each comes from, the shape of what it produces, the scenarios.
2. Write `SKILL.md` (numbered steps, each ending in "Done when") and the reference files; keep `SKILL.md` under 150 lines.
3. Write at least three scenarios whose checks cite rule IDs and document sections.
4. Run `python3 scripts/validate.py --skill <name>` until it is green, then `scripts/run-scenario.sh --skill <name> --host claude --scenario S01`.
5. Fill `skills/<name>/README.md` and add the skill under `## [Unreleased]` in `CHANGELOG.md`; the next release tag ships it ([`docs/releasing.md`](docs/releasing.md)).

## Running a scenario against a model

```bash
scripts/run-scenario.sh --skill <name> --host claude --scenario S02      # needs the claude CLI
scripts/run-scenario.sh --skill <name> --host codex  --scenario S02      # needs the codex CLI
```

Results land in `.eval-results/<name>/<label>-<host>/` with `results.json`
and `summary.md`. The eval workflow runs the same script weekly, on request
and on pull requests that touch a skill.

## Style

- Markdown for agents follows the pattern doc: steps with completion criteria, leading words, capability verbs, positive phrasing, no host tool names.
- Shell scripts stay compatible with macOS bash 3.2; Python scripts use the standard library only (PyYAML is used when present, never required).
- Host facts carry the date they were checked and the URL they were checked against.

## Releasing

See [`docs/releasing.md`](docs/releasing.md). Tags are `vX.Y.Z` and release every skill at the repository version.
